# Gemini研究指示の非公開管理経路・共有台帳設計（オフライン設計、未有効化）

## 境界
- 既存Render Web Serviceは公開到達可能（IP allow list `0.0.0.0/0`）。`app.py` にGemini送信HTTPルートを追加しない。公開URLの到達性を管理者認証と見なさない。
- 送信処理は独立した管理ジョブ／明示的な管理実行からのみ起動する設計とし、認証済み実行主体、対象commit SHA、`assignment_id`、`source_run_id`、審査対象本文の同一性を事前に確認する。管理ジョブの具体的な認証方式・権限・起動手段は未選定・未実証。定期CIや一般的な「次へ」は起動権限にならない。
- ネットワーク・Secret読取・課金API送信はそれぞれ個別のHuman Gateが成立するまで禁止。承認合図のみを認証情報として使用しない。Gemini応答からCodex、MAIN、実DB、決済へ権限を継承しない。

## 台帳の必要条件
- `research_lab/gemini_assignment_send_gate.py` は既存SQLiteファイル上で `BEGIN IMMEDIATE` と `assignment_id` 主キーによる原子的予約を行い、ファイル不在・重複・DB例外時は拒否する。これは単一の持続するファイルを共有する場合のオフライン実装であり、Render一時ファイルの再起動／再デプロイ耐久性を証明しない。
- 本番相当の送信経路では、全実行者が共有する永続ストレージ、原子的な一意制約、障害時の復旧方針、管理者以外の初期化禁止を実環境で確認する。Supabase等を使う場合も接続・DDL・書込は別途承認が必要。未検証のままSQLiteを共有台帳と称さない。
- 予約後に通信結果が不明なら再送禁止。別の`source_run_id`で同じ`assignment_id`を使っても拒否する。台帳の消失・接続失敗時は新規送信を停止し、自動再作成しない。

## オフライン受入基準
1. 未認証・未承認・CI SHA不一致・予算異常・台帳未検証なら送信処理へ進まない。
2. 共有予約を疑似実行し、同じIDの並行実行で成功は最大1件。別runの重複、結果不明後の再試行、台帳不在は拒否。
3. 疑似通信の成功／失敗／結果不明をテストし、秘密値をログに記録しない。APIキーはテストで参照しない。
4. 既存`review_assignment_preflight`の`ready_for_separate_runtime_review`はレビュー用判定のみ。戻り値の実行許可フラグは常にfalse。実行環境での認証・共有永続性・課金制御の証拠を別に要求する。
